# Repo conventions

Rules for writing or changing dbt code and lessons in this repo. The `kimball-modeler` agent follows these when it
generates code, and checks for them when it reviews.

## Layout

| Layer | Folder | Prefix | Materialization | Rules |
|---|---|---|---|---|
| Seeds | `dbt/seeds/` | `raw_` | seed | Generated by `dbt/scripts/generate_seeds.py`; never hand-edit CSVs |
| Staging | `dbt/models/staging/cascade/` | `stg_cascade__` | view | 1:1 with a seed. Rename, cast, trim, decode. No joins, no business logic |
| Intermediate | `dbt/models/intermediate/` | `int_` | view | Reusable logic: SCD history, allocations |
| Conformed dims | `dbt/models/marts/core/` | `dim_` | table | One model per conformed dimension |
| Process marts | `dbt/models/marts/<area>/` | `fct_`, `dim_`, `bridge_` | table / incremental | One folder per bus-matrix row |
| Aggregates | `dbt/models/marts/aggregates/` | `agg_` + shrunken `dim_` | table | Must tie to atomic facts |
| SCD lab | `dbt/models/marts/scd_lab/` | `scd_typeN_` | table / view | Teaching only |
| Semantic | `dbt/models/semantic/` | `sem_` | YAML | Semantic models + metrics |

## Keys

- Dimension surrogate key: `{{ dbt_utils.generate_surrogate_key([natural_key]) }}` for Type 1;
  `[natural_key, 'valid_from']` for Type 2. Name: `<entity>_key`.
- Durable key on Type 2 dimensions: `{{ dbt_utils.generate_surrogate_key([natural_key]) }}` as `<entity>_durable_key`.
  Put it on facts too (Type 7) when "as is" reporting is likely.
- Date keys are integers `YYYYMMDD` via the `date_key()` macro (arithmetic, not `to_char`).
- Role-playing FKs: `<role>_<entity>_key` (`ship_date_key`, `cashier_key`).
- Natural keys keep business names: `<entity>_id` or `<entity>_number`.

## Special members (every dimension)

- Append an Unknown row with `{{ unknown_member_row({...}) }}`, key `{{ unknown_key() }}` (= `'-1'`). The dict must
  list every column **in select order**.
- Use `'-2'` for legitimate "not applicable" cases with a meaningful label (Anonymous Shopper). In `dim_date`, `-1`
  = Unknown and `-2` = Not Yet Happened.
- Facts wrap every FK lookup in `{{ dim_key('d.<entity>_key') }}` so FKs are never null.

## Type 2 dimensions

- Columns: `valid_from`, `valid_to` (current = `{{ scd_end_of_time() }}` = `9999-12-31 23:59:59`, never null),
  `is_current`, `version_number`, optional `row_change_reason`.
- Prefer change-log reconstruction (`int_*_versions`, macro `scd2_from_change_log`) when a change log exists;
  otherwise dbt snapshots in `dbt/snapshots/snapshots.yml` with `dbt_valid_to_current`.
- Facts join point-in-time with a **half-open** interval:
  `and f.event_ts >= d.valid_from and f.event_ts < d.valid_to`. Never `between`.
- Test every Type 2 dimension with the generic `scd2_valid_ranges` test.

## Facts

- Header comment documents the **four steps** (process, grain, dimensions, facts). See `fct_retail_sales.sql`.
- Store **extended, additive** amounts; never stored ratios, percentages, unit prices or YTD values.
- Header-grain amounts are **allocated** with a tie-out test, or kept in a header-grain fact.
- Multi-currency: `<fact>_local` + `<fact>_usd` + `local_currency_key`.
- Lag facts: `<from>_to_<to>_lag_days`; counters: `<milestone>_count` (0/1).
- Incremental transaction facts: `merge`, `unique_key` = grain columns, lookback window, `cluster_by=['date_key']`
  for large tables. Stamp `'{{ invocation_id }}' as audit_key` where audit is wanted.

## Tests (minimum per model)

| Model | Tests |
|---|---|
| Staging | `unique` + `not_null` on natural keys; `accepted_values` on codes; `relationships` for codes used in joins |
| Dimension | `unique` + `not_null` on the surrogate key; `scd2_valid_ranges` if Type 2 |
| Fact | `dbt_utils.unique_combination_of_columns` on the grain; `dbt_utils.equal_rowcount` vs source; `not_null` + `relationships` on every FK |
| Bridge | uniqueness of the pair; weights sum to 1 (singular test) |
| Aggregate / allocation | singular tie-out test |
| Tricky logic | a unit test (`unit_tests:` in the model YAML) |

Generic test arguments go under `arguments:` (dbt 1.10+ syntax).

## SQL style (Snowflake dialect)

- Lowercase keywords, CTEs named for what they hold, `qualify` for window filters, `iff()`, `dateadd/datediff`,
  `group by all` where it reads well.
- Every model ends with a single final `select`.
- Avoid functions sqlglot can't transpile, or the DuckDB smoke test fails: no `ratio_to_report` (use
  `x / sum(x) over (...)`); `to_char` only with `YYYY`/`MM`/`DD` format parts.

## Lessons (site)

- `site/docs/<module>/<slug>.mdx`, front matter with `title`, `description`, `sidebar_position`.
- Start with `<KimballRef chapters={[..]} techniques={[..]} />` using Kimball's technique names.
- Show lab code with `<DbtFile path="models/..." />` (optionally `lines={[a, b]}`); never paste lab code by hand.
  The build fails on a missing file or out-of-range lines, so update `lines` when a model changes.
- End with a `<Quiz questions={[...]} />` and, where useful, an exercise in `<details>`.
- Links between lessons are absolute (`/scd/type-2`). No curly braces or bare `<` in prose (MDX).
- Write original explanations; never reproduce text from the book.

## Verify before committing

```bash
# dbt (no Snowflake needed)
cd dbt && dbt compile --profiles-dir ci && python scripts/smoke_test_duckdb.py
python scripts/build_lab_catalog.py          # refresh knowledge/lab-catalog.md
# site
cd site && npm run build
```
