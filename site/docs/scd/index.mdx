# Module 3: Slowly changing dimensions

Dimension attributes change: a product moves category, a customer moves city, an employee is promoted.
**What should history look like afterwards?** Kimball catalogs eight standard answers, Types 0 to 7, and the
right one is chosen **per attribute**, not per table.

## The running example

On **2025-03-01**, Cascade moved *Wool Hiking Socks* (SKU-2004) from category **Footwear** to **Socks &
Accessories**. Before that date it sold \$17,034.00; after, \$42,202.80. Each SCD type answers "what category do
those sales belong to?" differently.

| Type | Kimball name | Technique | Sales Jan–Feb report under | History? |
|---|---|---|---|---|
| 0 | Retain Original | Never change the value | Footwear forever (original category) | Original only |
| 1 | Overwrite | Update in place | Socks & Accessories (current) | None |
| 2 | Add New Row | New version row with effective dates | Footwear (as it was) | Full |
| 3 | Add New Attribute | `prior_category` column | Either, one prior value | One level |
| 4 | Add Mini-Dimension | Volatile attributes split into a banded mini-dim; fact carries both keys | (for rapidly changing attributes) | In the fact |
| 5 | Add Mini-Dimension and Type 1 Outrigger | Type 4 + current mini-dim key on the base dim | (current profile without the fact) | In the fact + current |
| 6 | Add Type 1 Attributes to Type 2 Dimension | Type 2 rows also carry current values | Either, from one join | Full + current |
| 7 | Dual Type 1 and Type 2 Dimensions | Fact carries surrogate *and* durable key | Either, by choice of join | Full + current |

Run `analyses/as_was_vs_as_is.sql` in the lab to see Type 2 vs Type 7 side by side.
