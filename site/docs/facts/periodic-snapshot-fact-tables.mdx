# Periodic snapshot fact tables

<KimballRef chapters={[4, 7, 9]} techniques={['Periodic Snapshot Fact Tables', 'Additive, Semi-Additive, Non-Additive Facts']}>
Inventory (Ch. 4) introduces the periodic snapshot; it recurs for GL balances (Ch. 7) and headcount (Ch. 9).
</KimballRef>

Some questions are about **state**, not events: *How much inventory is on hand? What's the account balance?
How many employees do we have?* You can in principle derive state by summing every transaction since the
beginning of time, but it's expensive and fragile. A **periodic snapshot** records the state at regular
intervals instead.

- **Grain:** one row per entity per period (day, week, month), e.g. one row per product per store per day.
- **Dense:** a row exists for every entity in every period, *even if nothing changed*. Zero is a value.
- **Predictable size:** entities × periods.
- Facts are typically **semi-additive levels** (on hand, balance) plus **additive period totals** (activity
  during the period).

## dbt and Snowflake notes

- **Incremental by period.** A daily snapshot is naturally `incremental` with `unique_key` = the grain and a
  filter on the snapshot date. Closed periods never change.
- **Generating density.** If the source only provides changes, build the dense grid by cross-joining a date
  spine with the entity list, then fill forward with
  `last_value(x ignore nulls) over (partition by ... order by date)`.
- **Volume.** 10,000 SKUs × 500 stores × 365 days is 1.8 billion rows a year. That's fine for Snowflake when
  clustered by date, but consider weekly or month-end snapshots for older history.

## Pitfalls

- **Sparse snapshots.** Leaving out rows where nothing changed means "sum of on hand across products" silently
  skips items. Snapshots should be dense.
- **Summing balances over time.** See [additivity](./additivity).
- **Snapshotting the wrong moment.** Declare *when* in the period the snapshot is taken (end of day? start?).
  It's part of the grain.
