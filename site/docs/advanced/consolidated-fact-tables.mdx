## Drill-across: the general technique

To compare facts from two processes, Kimball's method (**multipass SQL**) is:

1. query each fact table **separately**, aggregated to the same grain on conformed dimensions;
2. **merge the result sets** on those conformed attributes (a full outer join).

Never join two atomic fact tables directly on their dimension keys: the many-to-many relationship fans out
and inflates both sides.

```sql
-- ✗ WRONG: each sale row matches each inventory row for the same product/store/day
select sum(s.extended_net_sales_amount), sum(i.quantity_on_hand)
from fct_retail_sales s
join fct_inventory_daily_snapshot i
  on i.product_key = s.product_key and i.store_key = s.store_key and i.date_key = s.date_key;
```

The correct version is in `analyses/drill_across_sales_vs_inventory.sql` (see
[Periodic snapshots](/facts/periodic-snapshot-fact-tables#drill-across-to-combine-with-transactions)).

## Consolidated fact tables

When a particular drill-across is needed constantly, materialize it: a **consolidated fact table** holds facts
from several processes at a common grain. The most common example is budget vs actual:

<DbtFile path="models/marts/accounting/fct_budget_vs_actual.sql" />

- **Common grain first.** Budgets exist per account per month, so actuals are rolled up to that grain.
- **Full outer join** keeps budgeted-but-no-actuals and unbudgeted-actuals rows.
- **Derived variance** is stored because everyone needs it. It's additive, since both components are.

Other consolidated examples: actual vs forecast, sales vs returns by product-week, plan vs actual production.
